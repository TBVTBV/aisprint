# Interview Synthesis

## What this skill is for

Qualitative research is only as trustworthy as the discipline behind turning raw talk into claims. The most common failure mode is quiet: a single vivid quote from one interview gets treated, a few paragraphs later, as if it were a validated pattern. This skill exists to make that jump visible and to stop it from happening by accident.

The core idea, borrowed from good research practice: a claim only earns the label **Finding** once it is independently corroborated by more than one real source. Everything else — a single striking quote, a hunch, a synthetic/AI-generated interview used to stress-test a hypothesis — is real and useful, but it is a **Directional** signal, not a Finding, and the output must never blur the two.

## Workflow

### Step 1 — Ingest every transcript

Transcripts can arrive in any format — plain text, markdown, PDF, docx, even a photo of handwritten notes. Auto-detect the format per file and read it with the right tool:
- `.txt` / `.md` — read directly
- `.pdf` — consult the pdf-reading skill
- `.docx` — consult the docx skill
- images of notes — read visually

Don't ask the user to convert files first; that friction is exactly what this skill should remove.

### Step 2 — Classify each source before reading it for content

For every transcript, determine:
1. **Participant/role** (e.g., "Pediatric pulmonologist, Clalit" — anonymize to role + setting if the transcript contains a real name and the user hasn't already anonymized it)
2. **Real or synthetic.** A source is synthetic if it was generated by an LLM, is a hypothetical/composite persona, or is otherwise not an actual recorded conversation with a real person. Look for explicit labels ("synthetic," "generated," "AI persona") first. If a transcript's status is genuinely ambiguous, ask the user rather than guessing — this classification is load-bearing for everything downstream, and a wrong guess here silently corrupts the corroboration count.

Keep this classification attached to every quote and observation you pull from the transcript. It has to survive all the way to the final output.

### Step 3 — Write a per-interview debrief

For each transcript, extract observations in the source's own language — don't paraphrase away specificity. If the user supplied an interview guide or a topic spine (e.g., "current process → concrete example → what breaks → what would help"), organize the debrief around it; otherwise, organize around whatever structure the conversation naturally took. Pull direct quotes with enough surrounding context to know what question prompted them.

### Step 4 — Cluster into candidate themes

Read across all debriefs and group observations that point at the same underlying claim, even when the wording differs a lot between sources — physicians rarely use identical phrasing for the same complaint. Note contradictions explicitly rather than smoothing them over: a disagreement between two sources (or between a source and a record) is often itself the finding, not noise to discard.

### Step 5 — Apply the corroboration threshold

Default threshold: **2 independent real sources**. The user may set a different threshold — ask if they haven't specified one and the project seems to warrant it (e.g., a very small or very large source pool).

For each candidate theme:
- **≥ threshold independent real sources agree** → label it a **Finding**.
- **Fewer real sources, but synthetic sources also point here** → label it **Directional**, and say explicitly which part of the support is real vs. synthetic (e.g., "1 real source + 3 synthetic"). Never let a stack of synthetic sources push a claim over the threshold into Finding status — synthetic sources don't count toward the corroboration number, no matter how many there are.
- **Only synthetic sources support it, no real corroboration yet** → still surface it, tagged **Directional (synthetic only)** — this is a hypothesis worth testing with real participants next, not something to bury in an appendix.
- **Single real source, no synthetic backup** → **Single-source observation** — worth keeping visible (it may be exactly right), but never dressed up as a Finding.

### Step 6 — Produce the output

Always produce both layers in one document:

**1. Findings table** (for fast review):

| # | Claim | Status | Supporting sources | Representative quote |
|---|---|---|---|---|
| 1 | [one-sentence claim] | Finding / Directional / Single-source | [count + real vs. synthetic breakdown] | "[quote]" — [role, setting] |

**2. Expandable narrative report**, one section per row, in descending order of status strength (Findings first, then Directional, then single-source observations). Each section: the claim stated plainly, 2-4 sentences of context, the supporting quotes with attribution, and — if relevant — the contradiction or nuance that makes it interesting rather than obvious.

Close with a short **Guardrail / gaps** note: what the corroboration threshold was, how many total real vs. synthetic sources went in, and which Directional items most need a real source to confirm them next.

## Why this matters (read before skipping steps)

It's tempting to skip straight to writing polished-sounding findings — the raw material is right there and the model is good at prose. Resist that. The value of this skill isn't the writing, it's the bookkeeping: keeping every claim honestly tied to how many independent real people actually said it. A findings report that reads confidently but quietly promotes a single quote to "the pattern" will mislead the very people relying on it to make product or clinical decisions. When in doubt about whether something clears the bar, err toward labeling it Directional and say why — that's more useful than a false Finding.

## Handling translated or non-English transcripts

If a transcript is in a language other than the one the output should be written in, translate quotes but flag them clearly as team/AI translations rather than verbatim originals (e.g., append "— translated"). Don't present a translation with the same confidence as a verbatim quote.

## Output format

Default to a single markdown file (findings table + narrative report) so it's easy to skim and easy to hand to teammates. If the user's request implies a fuller deliverable (e.g., "write this up as our research report"), fold the same findings table and narrative into the appropriate report structure instead of producing two separate documents.
